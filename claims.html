Claims Integrity

The claim was correct. The paperwork wasn't.

Middleware that sits between an Emergency Department's records and the TPA or PM-JAY portal. It reads the notes, checks them against the evidence a payer will ask for, and produces the codes the documentation actually supports — while the patient is still admitted and a gap can still be closed.

How it decides

Evidence decides. Rules check. A coder signs.

Evidence decides

Every code traces to the exact words in a document. A finding that cannot be matched back to the source text is dropped, not surfaced.

Rules check

A versioned library of evidence rules, each naming the payer circular it comes from. A rule change is a data file, not a release.

A coder signs

Nothing is submitted without a person approving it. A claim with an unresolved evidence gap cannot be submitted at all.

Four steps, between the note and the portal

Read

Picks up ED notes, reports and discharge summaries from the existing system. Read-only — nothing is written back.

Check

Matches every claimed procedure against the evidence a payer requires — the right report, in the right document, in the right time window.

Code

Produces the ICD-10 and package codes the documentation supports, each with the exact source text it came from.

Flag

Tells the coder what is missing and how to fix it, before the claim leaves the building.

A flagged claim

Confident about the code. Still blocked.

This is real output from the engine on a synthetic case, chosen because it is the instructive one: the coding is not in doubt, and the claim is blocked anyway — because the payer judges the operative record, not the admission note.

Denial risk and coding confidence are tracked separately on purpose. A confidently coded claim with a missing document is high risk, not low — the payer rejects it regardless of how sure the system is about the code.

Connecting

Works with the EMR already in place.

India has hundreds of hospital systems and no two shape their data the same way. So the middleware does not integrate with EMRs one at a time — each one is described by a small configuration file, and everything after that point is identical.

Adding a vendor
A configuration file, not a software release
Develop against
A single saved payload — no credentials, no live data needed to start
Fallback route
A scheduled folder export. Needs nobody's permission, always works
Standards route
Generic FHIR R4, for any ABDM-aligned system
# the entire integration for a new EMR
id: your-emr
transport: rest_json

mapping:
  episode_id: encounter.id
  encounter:
    admitted_at: {_datetime: encounter.admit_datetime}
    procedure_time: {_datetime: surgery.start_datetime}
  documents:
    _each: clinical_notes
    _as:
      text: {_first: [note_text, body, content]}
      doc_type:
        _map: note_type
        _table: {"OT Note": op_note, "Discharge Summary": discharge_summary}

A profile is marked verified only once its field paths are checked against that vendor's real payload. An unverified profile cannot be run against a live system.

Where the data sits

Patient data does not leave the hospital to be useful.

Read, never written

The connection to the EMR is read-only, permanently. There is no path by which this writes back into the clinical record.

Processed on-premise

Reading, checking and coding all happen on a box inside the hospital's own network — not in our cloud.

De-identified before export

Improving the model needs examples. Anything that leaves is stripped of identifiers first, or it does not leave at all.

The unit of export is the episode: one identifier the de-identification service is not certain about holds the whole episode back, rather than guessing in either direction. Nothing is exported by default — training export is off unless a hospital's contract turns it on.
